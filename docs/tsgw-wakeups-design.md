# Wakeups 综合改进方案

状态：方案 v1，用户已批准；独立 worktree 实施、隔离验收和代码定向复核完成。日期：2026-11-16（UTC+08:00）。

本文件承载本轮需求、已批准的设计取舍和验收标准；运行维护契约见[模块规则](../tsgw/wakeups/AGENTS.md)，工具使用见[调用技能](../tsgw/wakeups/skills/tsgw-session-wakeup/SKILL.md)。本方案按用户要求集中保存在文档目录，不另建规划或状态台账。

## 1. 目标与完成标准

| 编号 | 当前问题 | 改进目标 | 完成标准 |
| --- | --- | --- | --- |
| R1 | 到点后任务离开 pending 列表；历史仅记到 accepted/queued，用户需要查目标会话 | 直接观察投递及处理状态 | 来源会话有可见入口；按 wakeupId 可查询；UI 与工具使用同一记录；明确区分接受、通知收到、所在运行结束及未知 |
| R2 | 调度仅接受已经持久化的会话 ID，需要手工先建会话 | 按项目创建普通新会话并安排唤醒 | 一次工具调用指定项目目录、时间及交接内容，返回真实目标 ID 和可打开的会话；加载目标项目自己的规则 |
| R3 | 计时器仅存内存，服务重启后丢失 | 持久化尚未触发任务并在服务启动恢复 | 无需先打开浏览器或会话即可恢复；取消、已投递和结果未知的任务不会因恢复而重复发送 |

三项属于同一条任务生命周期，应共用持久化记录、任务 ID 和目标会话绑定。业务验收仍由实际执行任务决定；宿主只证明它能够观察到的投递与处理事实。

本轮范围限于一次性 wakeup。不引入周期任务、数据库、独立调度服务、自动重试、自动新建项目目录、源会话完整上下文复制或新的权限继承机制。初始实施授权不包含提交、推送、发布、部署及真实服务重启；后续合并与发布授权见第 7 节。

## 2. 实施前核实的基线

- `scheduler.ts` 用 Map 和 `setTimeout().unref()` 保存尚未触发项，到点先从 Map 移除，再调用投递函数。
- `runtime.ts` 在目标会话记录 `created/cancelled/submitted/failed`，`list()` 仅返回内存待执行项。
- `host.ts::submitWakeup()` 使用 SDK 的 `sendCustomMessage(..., { deliverAs: "followUp", triggerTurn: true })`；接受或排队即返回，不等待目标任务完成。
- `history.ts` 只聚合 `pi-web:wakeup` custom meta；当前只读文件路径主动跳过普通消息，不能据此判断通知是否真正进入目标上下文。
- `getWakeupRuntime()` 使用 `Symbol.for` 复用同进程 runtime，不提供进程重启恢复；目前第一次启动普通会话才创建 runtime。
- `app/api/agent/new/route.ts` 已能按 cwd 创建普通会话，但会初始化 wrapper。SDK 1.5.2 的 `SessionManager.create()` 本身不立即写盘；按现有 `lib/session-fork.ts` 先例显式保存 SDK header/entries 后重开，可以建立无 wrapper 的持久化普通会话。临时目录探针已通过保存、重开、追加及 SDK 列表发现。
- `instrumentation-node.ts` 是服务启动接线入口，已有 IM 未提交改动。wakeup 接线必须保留该改动；不修改 IM 模块、包依赖和锁文件。

## 3. 核心设计

### 3.1 一份持久化任务记录

建议在 `getAgentDir()/integrations/wakeups/state.json` 保存带版本号的任务记录。其职责包括恢复清单及可查询的最近状态；会话 custom meta 继续作为审计记录，不能反向推导或恢复所有历史 `created`。

每个任务至少包含：wakeupId、来源会话、目标会话、目标项目目录、创建及预定时间、交接内容、当前状态、状态变化时间，以及有证据时的通知 entry ID、分支身份、宿主运行关联 ID、相关响应 entry ID、失败原因。接受、通知收到和运行终结分别保存证据及时间；状态由已确认的证据投影，不取最后一条事件直接覆盖。新会话绑定与后续状态沿用同一 wakeupId。

状态文件采用项目已有原子替换能力，目录权限 0700、文件 0600；读写按同一个 runtime 串行化，状态转移检查最新状态，取消与触发只能有一个先取得 pending 的处理权。不另加依赖。文件缺失表示尚未使用新机制；版本未知或内容损坏应报告错误并保留原文件，不能默默清空后继续接受调度。

运行状态提交先于对应副作用：

1. 创建先确认输入及目标，再持久化 pending，随后挂计时器并返回成功。
2. 取消仅对最新状态仍为 pending 的任务生效，先持久化 cancelled，再移除未触发计时器；持久化失败不得声称取消成功，触发已取得处理权时明确拒绝取消。
3. 触发前先把 pending 持久化为 dispatching，写入失败则不发送。
4. 发送被接受后记 submitted；审计写失败不得把已接受消息改报为发送失败或自动重发。
5. 目标事件更新已确认的处理状态。无法可靠确定的结果保留 unknown。

会话审计与状态文件不具备跨文件原子性。调度成功与恢复以状态文件为准；审计追加失败明确记录诊断，不撤销已生效的调度，也不让调用者误以为必须重新创建。

**写入失败的固定处理：**状态文件写失败后，runtime 进入存储暂停状态，清除尚未触发的内存计时器，拒绝新增调度／取消及尚未提交的发送。保留磁盘最后可靠版本；内存已观察到但未持久化的证据仅以“本进程观察、未保存”展示，不能伪称已写成 unknown。查询同时返回存储健康和计时器是否实际挂起，不能只显示磁盘 pending 让人误以为正在等待触发。不对该任务自行重试写入或投递；修复存储并重新初始化所有者后，重新读盘恢复确定 pending。

| 失败点 | 磁盘与计时器 | 工具／查询结果 | 下次恢复 |
| --- | --- | --- | --- |
| 创建 pending 写失败 | 无新 pending；不挂新计时器；其他计时器暂停 | 创建失败；若已建会话，结构化返回该 ID | 不凭失败调用补造任务 |
| cancelled 写失败 | 原 pending 保留；所有计时器暂停 | 取消未确认生效，显示存储异常及原状态 | 原 pending 仍可恢复，不能声称已取消 |
| dispatching 写失败 | 仍为 pending；即使原 timer 已移除，也显式处于暂停状态 | 不发送，显示 pending＋调度暂停 | 修复后按 pending 恢复，适用逾期策略 |
| SDK 已接受，submitted 写失败 | 至少已有 dispatching；不回退 pending；暂停后续未提交发送 | 不报投递失败；展示已观察接受但未保存及存储异常 | 结果不明，不自动重投 |
| received／settled 写失败 | 保留最后可靠证据；暂停后续未提交发送 | 本进程可显示未保存观察；不伪造持久化终态 | 按目标通知补证；无法证明的运行终态待核实 |
| pending／cancelled 已保存，仅会话审计失败 | 权威状态及计时器按已提交结果生效 | 成功返回原字段和诊断；不得抛成未安排／未取消 | 按权威状态恢复；不补投已消费任务 |

第一版保留终态和交接正文，不自动永久删除；这是需要批准的数据保留取舍。UI 和新增查询支持分页，默认只展示当前会话相关任务；分页不减少整文件读写成本。首版按约 1000 条、总文件不超过 8 MiB 的日常规模验收，测量原子保存耗时及事件循环停顿，目标保存耗时 p95 不超过 100 ms；另以 10000 条／约 64 MiB 测量退化，不把该压力规模声明为已承诺容量。未通过日常规模验收时先修订存储方案，不以删数据或改低标准处理。容量导致读写失败时沿用暂停矩阵，不自动清理或静默转成纯内存模式。

### 3.2 投递与消费状态

本地 SDK 1.5.2 的公开事件支持以下状态，不单设无法精确证明的“模型开始处理”或“任务成功”：

| 展示状态 | 可靠依据 | 不能据此声称什么 |
| --- | --- | --- |
| 待触发 | 持久化 pending 任务 | 已经进入目标队列 |
| 投递中 | 先持久化 dispatching，再准备本次投递 | 目标已接收 |
| 已接受（可能排队） | 已知 wakeupId 的提交被 SDK 接受 | 通知已落盘、模型已经处理 |
| 通知已收到 | 原始 SDK 通知 message_start 的类型及 details.wakeupId 匹配 | 模型请求已发出、任务完成 |
| 所在运行已结束 | 通知关联的运行出现 agent_settled | 运行成功、子任务全部结束或业务验收通过 |
| 所在运行已中断 | 同一关联运行的 agent_settled.aborted 为 true | 本条要求从未执行、已有副作用已撤销 |
| 投递失败 | 本次确认接受前失败 | 可以自动安全重投 |
| 已取消 | 尚未触发任务的取消已经持久化 | 已撤回已投递或排队消息 |
| 待核实 | 重启或观察中断，缺少足够结果证据 | 任务一定失败或一定未执行 |

`host.ts` 当前接受后立即取消监听，需要由模块 observer 在服务器继续观察 wrapper 的原始 SDK 事件。通知按 wakeupId 匹配；运行关联持续到 `agent_settled`，不以重试中的 `agent_start` 重建，也不使用会重置的 turnIndex 作为持久化标识。当前 SSE 会裁剪通知 details，不在浏览器推断关联，更不能为了观察打开可能启动 wrapper 的目标 SSE。

同一运行包含多条 wakeup 或普通 follow-up 时，settled 是共享的运行事实；最终一条响应的错误不能自动归为每个 wakeup 的失败。auto retry、compaction 和扩展续发继续观察到 settled；子代理家族活动缺少逐条因果关系，不作为某个 wakeup 完成的依据。

SDK `clearQueue()` 会移除 custom 通知，但只返回普通文本队列；已出队的通知也可能在压缩或异步 turn_start 后才触发 message_start。本地纯内存探针已确认该窗口，因此不能用“已接受但未收到”的集合推断逐条 queue_cleared。Stop／Recall 仅记录发生事实，之后依据真正观察到的 received／settled 推进状态；缺证据时标待核实。要精确报告每条清队列结果，需要 SDK 提供实际移除消息的标识，不在本轮 patch 私有字段。

事件可能在 `sendCustomMessage()` 返回前发生；后追加的 submitted 不能把已经 received 或 settled 的状态倒退。`message_start` 只证明内存收到，`message_end` 也早于 SDK 落盘；持久化确认需要模块记录或只读目标文件中的完整通知。重启对账时只认原 targetSessionId 和分支证据，不把 fork 继承通知当成新消费。

不要求模型主动调用“确认消费”工具，也不自动给来源会话投递新的模型消息。需要业务级结论时，用户可打开相关响应查看原始报告；第一版不增加业务完成回执协议。

### 3.3 按项目创建目标会话

推荐扩展 `schedule_wakeup`，保留原有默认当前会话及 `session_id` 行为，新增 `cwd` 和可选 `title`：

| 参数选择 | 行为 |
| --- | --- |
| 不传 session_id/cwd | 当前普通会话 |
| session_id | 已存在的普通目标会话 |
| cwd，可选 title | 在该项目创建新的普通会话并将其作为目标 |

`session_id` 与 `cwd` 互斥；`title` 仅适用于新会话。校验现有、可访问的目录，沿用项目路径规范，不创建目录、不按显示名称猜路径、不自动挑选“同项目最近会话”。

推荐安排时创建并持久化目标，立即返回稳定 sessionId。这样用户可预先查看或补充信息，取消及重启恢复不需要再次分配目标。代价是取消后会保留可能尚未执行的会话；不自动删除它。

目标只接收交接消息，不复制来源会话上下文、凭据、临时工具选择、侧聊或子代理身份。创建时不选择模型或 thinking，不写工具 pin；首次启动 wrapper 时才按目标 cwd 加载项目规则、技能、扩展、trust 约束及现有默认配置。用户提前打开会话可能提前启动，因此配置既不是安排时快照，也不保证一定取到点时的值；首次启动后仍沿用宿主既有恢复语义。

SDK 1.5.2 的轻量创建路径已用临时目录验证：`SessionManager.create(cwd, sessionDir)` → 可选 `appendSessionInfo(title)` → 将 SDK `getHeader()/getEntries()` 序列化成 JSONL，以 `wx` 和 0600 创建文件 → 丢弃原 manager → 后续 owner 路径重新 `SessionManager.open()` 后追加。仅添加名称或 custom meta 不会使 SDK 首次自动落盘；显式写盘后继续使用原 manager 会留下未 flushed 的内部状态，因此重新打开这一步不可省略。不修改 SDK 私有字段。

探针未创建 AgentSession 或模型运行时，确认没有对话消息或 parent/fork 关系；SDK 列表可发现真实 ID 和名称。Web 侧栏、文件访问缓存及真实 host 集成仍属于实现验收。显式 title 直接持久化，不为命名调用模型；未指定名称时使用宿主现有无标题行为，不承诺通知正文自动成为标题。

新会话创建与 pending 记录也不具备跨文件事务。时间和参数先校验；创建成功但保存调度失败时返回已创建的 sessionId，说明“会话已创建，唤醒未安排”，方便复用，不自动删除或盲目再建。

暂不新增通用 `create_session` 工具。它会扩大到独立于 wakeup 的会话创建需求，本轮直接解决调度入口即可。

### 3.4 服务启动与恢复

在服务 Node 启动入口恢复 runtime，不依赖浏览器请求或首次会话启动。继续使用现有 owner、严格重开、admission、MCP 准备、followUp 和 Stop，不另建会话注册表或投递锁。

建议恢复策略：

| 持久化状态 | 服务启动后动作 |
| --- | --- |
| pending，尚未到期 | 按原时间挂计时器 |
| pending，停机期间到期 | 补投递一次，保留原预定时间并记录延迟恢复事实 |
| dispatching／submitted／已收到，缺少运行终结证据 | 针对该 wakeupId 只读核对目标记录；完整通知可确认曾收到，不能确认所在运行是否结束；证据不足标待核实，不自动重投 |
| 已取消、已结束、明确失败或中断 | 不恢复发送 |
| 旧版仅有会话历史 created | 不自动恢复，不将旧审计当作新调度来源 |

目标文件被删或目标变成子代理时记录确定失败，不创建替代会话；项目目录消失时沿用现有拒绝行为。不能仅凭调度状态文件恢复一个已经删除的目标。

恢复不是“保证恰好执行一次”。例如 dispatching 已保存、真正发送前进程退出，这次任务可能一次也没发出，但仍不会自动重投。发送与落盘之间的崩溃窗口无法靠本地 JSON 消除；本方案优先防止重复执行，为结果不明的项目保留明确状态与证据入口。

同一 agentDir 可能被多个实例共用。本机只读检查已确认：`pi-web-run` 中 30141 的 Pi Web 与 30142 的 TSGW 实例均仍有存活进程；未对这些服务执行任何修改。推荐复用已有 `proper-lockfile` 取得该状态目录的单一调度所有权：先取得锁的实例负责，其他实例只读，调度或取消明确返回“该清单由另一实例管理”。这是已批准的产品限制，不是唯一技术方案。首版不增加所有者选择配置；若要求固定实例负责或多个实例独立调度，先修订隔离／身份设计，不能按 PID 或端口临时猜分区。

所有权生命周期固定如下，主体留在 wakeup 模块：

- 锁基于独立目录路径，不锁会被原子替换的 state.json inode；由同进程全局 runtime 持有，热更新不重复竞争。
- 显式采用 stale 10 秒、每 5 秒更新；启动锁竞争通过库原生重试等待，最多 30 秒，不阻塞 Web 正常服务。这样异常退出后留下的锁能过期再接管；30 秒后仍由存活 owner 持有则本实例进入只读，并报告原因，不永久无声等待。
- 接管成功后重新读取和校验最新状态，再恢复 pending；不得用获取锁前的快照挂计时器。不自动轮询抢占存活 owner；只读实例后续接管需重新初始化或重启该实例，属于另行服务操作。
- 自定义 `onCompromised`，不得使用默认抛异常使整站退出。失锁后立即置所有者不可用，移除计时器，拒绝写入与新提交；中止本模块尚未提交的准备，并在异步准备结束后、实际调用发送前、每次状态保存前重新确认仍持有当前所有权。
- 已进入 SDK 发送的动作无法用锁撤回。失锁时不回退该任务为 pending、不尝试补发、不以过期内存覆盖新 owner 的文件；本进程仅保留诊断及未保存证据，新 owner 对 dispatching 保持待核实。
- 正常关闭先停止接受调度及未提交准备，再释放锁；已有 dispatching 保留。锁丢失不能靠自动重抢继续旧回调，恢复必须建立新所有者并重新读盘。

锁只保护参与该协议的 wakeup 状态读写，不约束其他版本或实例对目标会话的普通操作，也不解决多进程同会话写入或保证恰好一次。调度状态所有权与现有 wrapper owner／admission 是不同职责，不复制宿主会话注册表。

## 4. 用户入口与工具契约

建议 UI 与 AI 查询同时提供，但共用一份状态：

- 来源会话仅在有相关记录时增加紧凑的唤醒入口，显示待触发／未终结及待核实数量；打开列表查看与该会话关联的任务。不增加全局常驻工具栏或独立大盘。
- 列表包含摘要、项目、原预定时间、最新状态及来源／目标会话入口；提供关联响应入口，复用宿主已有 session／entry 搜索定位。深层历史、其他分支或尚未进入宿主会话列表的目标沿用上游打开会话回退，不新建 URL 定位协议或改写上游搜索范围。
- 列表只读；本轮保留现有工具取消能力，不同时加入浏览器新建、重新执行、周期规则等操作面板。
- UI 仅在打开列表时进行有限轮询；入口数量可随会话现有刷新机会更新，不另设全页常驻轮询。读取不得启动 wrapper、发送模型消息或延长目标会话租期。
- 原有 `list_wakeups({})` 保持 `Wakeup[]` 数组及原必需字段，包含 message；仍列本实例实际挂起的待执行计时器，不改为分页包装对象。实例暂停或非 owner 时可能为空，不能据此宣称磁盘无任务，技能改为优先使用带健康信息的新查询。
- 新增 `query_wakeups` 只读入口，支持 wakeupId、来源、目标、项目、状态过滤及分页，固定返回 `{ items, nextCursor, health }`。列表项默认只含摘要；按 wakeupId 详情查询才含交接正文及证据。health 明确 ready／starting／read_only／paused／storage_error 和原因，任务另含 armed 事实，区分磁盘 pending 与实际计时器。
- `schedule_wakeup` 正常成功保留原 Wakeup 顶层字段；新增诊断为可选字段。新会话已创建但 pending 未保存时，以 `isError: true` 和结构化 `{ code: "session_created_wakeup_not_scheduled", scheduled: false, targetSessionId }` 返回，不能只抛字符串或让调用者再建会话。
- `cancel_wakeup` 在 cancelled 已持久化后即按成功返回原 Wakeup 字段；后续审计失败只添加可选 diagnostics。状态写失败则返回带 code 的错误，明确 cancellationConfirmed 为 false；不把内存观察当作持久化成功。
- `list_session_wakeups` 保留旧版审计查询；任务状态查询不以它为唯一数据源。旧数据缺少消费证据时如实展示未跟踪，不补造新状态。成功、部分生效及错误分支同步更新工具 schema、技能和兼容用例。

后端新增模块专用只读接口 `GET /api/tsgw/wakeups` 及 `GET /api/tsgw/wakeups/[wakeupId]`，共用上述查询投影和 health；具体字段以本节为审批范围。暂不修改 `/api/agent/debug` 或 `/debug`，避免扩大 Debug 模块的后端契约。
